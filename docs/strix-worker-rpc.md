# Controlled Strix worker RPC

The production IPC surface separates a restricted installed Strix worker from controller effects. `strix_controlled_worker_rpc` owns local Linux Unix-domain socket I/O around the existing fifteen-method `ControlledControllerTransport` protocol. `strix_controlled_worker_channel` remains the pure message, identity, handle, and replay validator. `strix_controlled_worker_process` remains an inert development fixture and is not a production launch path.

The controller creates one attempt-private directory with mode `0700`, a `SOCK_SEQPACKET` socket with mode `0600`, and one listener. It supplies the exact attempt/profile binding and the reviewed effect transport. `OwnedWorkerProcess` immediately duplicates the spawning supervisor's Linux pidfd before asynchronous service can begin and refuses a numeric PID without stable custody. Its PID, UID, GID, start ticks, and pid-namespace chain form one custody identity. The server takes that descriptor exactly once and stops the channel when the owned process exits, including before authentication.

Connection-time `SO_PEERCRED` is only the first join. In the controller-bound socket mode, the worker sees the controller as listener creator. In the descriptor-bound private-root mode, the guest creates the listener before transferring its FD to the controller, so the worker sees its own guest identity at connection time. The controller's later packets must still carry the exact controller TGID, UID, and GID. Both endpoints enable `SO_PASSCRED`, receive every bounded packet with `recvmsg`, and check kernel-supplied credentials before reassembly or dispatch. Linux reports the process TGID for a sending thread, so pinned Strix's same-process threads remain usable without a `/proc` lookup while a forked child or another same-UID process cannot continue the channel with an inherited or transferred descriptor. Large canonical worker frames are split into ordered 64 KiB packets with exact frame identity, total length, offset, terminal marker, credentials, and one absolute deadline. Every nonterminal packet must be full-sized, packet count is bounded, and the loop yields while enforcing its deadline. Missing or truncated credentials, sender changes, undersized intermediate packets, reordered or repeated packets, partial frames, or an oversized frame permanently abandon the channel. Production admission must separately establish that the worker has no capability that can forge another process identity.

The launch file, socket node, and their private `0700` directory must be published to the worker's exact effective UID while the already-open listener remains controller-owned. The worker verifies that filesystem owner separately from the controller process PID, UID, and GID it authenticates through `SO_PEERCRED` and per-packet credentials. The first supported native launcher uses a fresh host UID/GID, private mount/network/IPC/UTS boundaries, and the host PID namespace so controller and worker TGIDs remain exact; it must report `pid_namespace_isolated=false` rather than implying PID-namespace isolation. Publication and cleanup of the exact private path remain launcher responsibilities and still require installed Linux qualification.

`strix_controlled_worker_launch` writes bounded launch material as a newly created `0600` file inside the private directory. The protected child environment carries only `BLUEFIRE_STRIX_WORKER_LAUNCH_FILE`, the file's path, plus allowed locale values. The token is absent from argv, environment values, ordinary representations, and public evidence. The worker verifies the file's owner, type, mode, and link count and unlinks it before connecting. The material binds the socket, token, controller process, protocol attempt identity, exact bootstrap environment, injected installed package identities, and one `StrixLaunchPlan` projection whose digest must equal the worker binding's plan digest. The projection validates the fixed upstream option inventory, target and model-gateway identities, budgets, runtime environment, workspace paths, and immutable objective/configuration bytes. The daemon must obtain package and plan identities from verified installed artifacts and accepted product state; the material itself does not prove their provenance.

The fixed native launcher uses `/runtime/bin/python -I -S -B -X utf8 /bootstrap/worker.py`; the immutable bootstrap arms the admitted no-exec/no-child-process boundary before adding the exact installed site-packages and entering `bluefire.strix_controlled_installed_worker`. The worker accepts no caller arguments. It requires the exact four-variable bootstrap environment (`BLUEFIRE_STRIX_WORKER_LAUNCH_FILE`, `LANG=C`, `LC_ALL=C`, and `PATH=/runtime/bin`), protected one-use material, authenticated RPC, and complete bootstrap identities before calling `strix_controlled_bootstrap`.

Two versioned input projections remain distinct. The legacy non-pivot `proc_memfd` mode validates the controller-prepared workspace, copies the objective/configuration/MCP bytes into sealed non-inheritable memfds, and derives only three `/proc/self/fd` arguments. The native `descriptor_bind_files` mode never reopens or chdirs into host paths. The helper verifies the same three sealed memfds before pivot, bind-mounts their exact inodes read-only, `nodev`, `nosuid`, and `noexec` at `/inputs/objective.json`, `/inputs/config.json`, and `/inputs/mcp.json`, and omits `/proc`. The worker revalidates the seals and digests, the read-only `/runtime/bin/strix` executable, private `0700` `/workspace`, `/home/worker`, and `/tmp` directories, then projects argv, cwd, HOME, and TMPDIR only to those fixed guest paths. Launch material carries the exact projection ref. The host source paths and bytes remain controller-validated prelaunch and are bound into the invocation and native activation, but never assumed present inside the pivot.

`STRIX_RUNTIME_BACKEND` is `bluefire-controlled`. The reviewed startup overlay keeps the official CLI lifecycle while limiting Docker setup to the Docker backend. During `_bootstrap_scan`, it skips upstream `persist_current()` only for `bluefire-controlled`, so the attempt-scoped `LLM_API_KEY` relay bearer remains in memory and is not written into Strix configuration. Other backends retain upstream persistence. The bootstrap still validates the exact installed versions, candidate digests, startup-overlay receipt/ref, and projection ref before importing Strix. Bootstrap-only identities, including the historical `DOCKER_HOST` metadata string, are passed to that validator but excluded from the official CLI's process environment; the controller also exposes no Docker socket in the worker's filesystem.

The launch file contains only the model-relay authorization digest, never the relay bearer or provider credential. The server also requires a one-use `ControlledWorkerContainmentAuthorityV1` whose live verifier owns controller-private kernel descriptors, matches the RPC pidfd custody identity, and rechecks the admitted containment immediately, before model authority, and before every effect admission. A serialized containment receipt is evidence only and cannot satisfy this interface. The admitted implementation must allow only bounded same-TGID threads required by pinned Strix while denying child processes, process-changing exec, namespace escape, and direct unapproved network paths. The exact containment implementation and pinned-engine compatibility still require installed Linux qualification.

After token, binding, containment, stable-process, and per-packet credential checks pass, the controller claims one attempt-bound model-gateway lease and returns its ephemeral relay bearer in the private acknowledgement. Any failed or ambiguous acknowledgement consumes and revokes the lease, and a failed revocation remains retryable reconciliation work. The installed worker exposes the bearer only as `LLM_API_KEY` while the official Strix main is active, then scrubs it and closes the transport. The bearer is defense in depth, not the kernel authority: production admission also requires the private relay and containment to make it unusable by another process. Controller shutdown revokes the relay lease. The protected gateway, not this token, owns the actual provider authorization and usage limits.

Each message retains the existing protocol version, attempt/claim/plan/profile/execution/fence binding, channel nonce, deadline, sequence, and request identity. Admission occurs in packet order. Frame sizes are checked before allocation and handshakes use a smaller bound than ordinary request and response frames. Reads, writes, authentication, and responses have absolute deadlines. Controller reply validation uses the clock after the effect settles. The async transport permits the existing bounded exec/cancel overlap while preserving response sequence and request joins.

Malformed frames, replay, wrong peer or token, out-of-order messages, partial I/O, EOF, cancellation, or an expired deadline permanently abandon the channel. The controller closes admission and accepted streams before waiting for dispatched coroutines to settle. Repeated cancellation does not release that settlement wait. Coroutine settlement is not evidence that an external effect or worker process has ceased: the daemon retains process ownership, effect custody, fencing, reconciliation, and durable receipts.

## Daemon integration still required

This increment provides a controller server, protected material writer/reader, worker transport, and fixed entrypoint. It does not connect those pieces into `EngineWorkerRuntime`, whose current launch continues to use `stdin=DEVNULL`, and it does not launch Strix or effects in tests. The future daemon composition must:

1. Verify the admitted installed interpreter, worker package, Strix candidate, and SDK artifacts and derive their exact identities.
2. Create the server and one-use material under a protected runtime parent, bind the file path into the immutable exact child environment, launch the owned installed entrypoint, then construct `OwnedWorkerProcess` from the spawn-owned pidfd before any asynchronous handoff.
3. Supply the matching controller-private `ControlledWorkerContainmentAuthorityV1` to `serve`. Its live verifier, not a JSON receipt, must re-open and compare the admitted process, seccomp, cgroup, namespace, filesystem, and relay boundaries. The worker must receive no Docker socket, host-command authority, provider credential, direct target route, or general network capability. Python IPC validation does not itself implement that OS boundary.
4. Supervise server, process, deadlines, and cancellation together; retain controller effect custody until settlement and verified external cessation or explicit reconciliation.
5. Remove abandoned launch material and the attempt-private directory after the worker and server are settled. Do not publish tokens or material in evidence, process logs, or crash reports.

The architecture policy places the production bootstrap and IPC modules in `controlled_worker`. That layer can import only itself and pure domain/foundation modules; imports of execution-layer Docker/effect implementations are refused. Controller execution composition may depend on this layer. The inert process fixture remains in the separate execution layer.
