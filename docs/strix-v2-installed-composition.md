# Installed Strix V2 composition status

The installed Strix path remains closed. The V2 opener now defines the protected
application-level join, but it does not treat declarations, fixtures, or protocol
objects as proof that Strix executed.

Execution first reserves the exact service `ProductStore`, accepted execution
claim, current runtime resolution, and canonical V2 admission as an immutable
prelaunch authority. Resource allocation runs under that authority. Only after
the fixed worker and other owned resources produce observed receipts may the
store retain activation; model and tool effects remain closed until that
activation is reopened and validated. The activation binds the controlled launch,
qualified component set, atomic exec-dispatch authority, crash-surviving operation
watchdog, worker launch and consumed containment verifier, and all six lifecycle
owners. The installed launch identity separately binds the exact reviewed startup
overlay receipt, prelaunch Linux runtime-closure plan, observed fixed-exec receipt,
prelaunch target-scope admission, sealed installed projection, and fixed-path
input set. It also binds the exact runtime-image contract, qualification, closure,
and minimal `bluefire-strix-worker` distribution identity. A full product wheel
cannot substitute for that worker identity. None can be inferred from the
aggregate launch digest, and a closure plan without observed fixed-exec proof is
unavailable.
For a real Caido sidecar it also requires exact protected receipts for the owner's
terms acceptance, current plan entitlement, and separately acquired digest-pinned
sidecar. BlueFire does not bundle, modify, or publish that sidecar. A distinct
MIT-wire-fixture test provider may satisfy deterministic protocol startup only;
its activation has no terms or entitlement refs, is permanently marked as not
live proof, and cannot be substituted for the real provider identity.
The controlled Test model provider is likewise marked as not live model proof.
The retained custody-bound model lease must carry the same Test/live proof class;
an opaque ref cannot relabel it.

The opener rereads durable authority immediately before allocation, after
allocation, and after runtime construction. The runtime must retain the same
dispatch runtime and authority, reviewed Docker transport, continuous operation
watchdog, controller server with its consumed live containment verifier, model
lease, source collector, and admitted target relay supplied by the protected
adapters. Cancellation must verify that it owns that exact dispatch authority.
The controller server must retain that exact model lease and return an exact
custody-ready receipt after worker, containment, projection, sealed inputs, and
custody are live; scheduling `serve()` is not readiness.
An aborted transaction must return a bound verified-absence receipt, including
when allocation stopped before activation; an ordinary
`close()` return is not accepted as cleanup proof. When abort cleanup also fails,
the typed error retains both the triggering failure and every cleanup failure.

Reconciliation is a different path. It receives no launch plan, model lease,
exec attachment, or live worker controller. It uses an exact historical runtime
identity plus cleanup-only custody, settlement, observation, and containment
owners. Its runtime has no callable execution entry point. Current code never
recomputes historical launch bytes during recovery.

The following concrete joins remain required before installed execution can be
advertised or enabled:

- the reviewed Docker attached-stream transport and V2 exec admission authority;
- a protected external watchdog backend that survives controller loss and proves
  whole-container stop and absence through the complete operation deadline;
- the controller-owned worker RPC plus its exact same-TGID, no-child-process,
  no-exec containment authority;
- durable ProductStore sources for the canonical admission, activation,
  historical identity, startup overlay, closure/fixed-exec qualification, target
  scope, Caido entitlement, and resource and terminal-settlement receipts;
- the controlled provider, target relay, independent observer, completion, and
  source-settlement owners; and
- installed qualification exercising startup, real tool traffic, cancellation,
  cleanup, and retained evidence.

The official CLI also treats every API-spec base URL as target authority and may
rewrite localhost targets to `host.docker.internal`. Execution therefore requires
the separate exact target-scope admission and refuses the legacy scope-only path;
objective text is never parsed as an implicit grant by this opener.

Until every join is present and the installed qualification passes, the stock
Docker backend is not an alternative and the product must report installed Strix
execution as unavailable.
