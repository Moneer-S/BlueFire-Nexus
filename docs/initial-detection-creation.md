# Create a rule from a completed run

The contextual Assistant can propose an initial SQLite or Sigma rule from a verified completed run. This does not require an existing candidate or create a placeholder hypothesis in the registry. The operator selects a named observed behavior, source language and development case role before asking for assistance.

`POST /assistance/detection-source` accepts `{run_id}` and reads the finalized bundle and independently observed records. It returns the immutable source binding, human run title, observation counts, named behavior choices and actual parser availability. No model is called. `POST /assistance/detection-context` binds the selected `run_id`, `source_binding_digest`, `behavior_id`, `target_language` and `case_role`. Ambiguous behavior choices remain operator choices. Creation requires 1–128 observed records; records are not silently truncated. Held-out is not an allowed creation-source role.

Submit the existing `/assistance/turns` request with selection kind `run_detection`. The fixed capability is `detection.create_and_evaluate`; the model chooses only the authoritative available capability. Off makes no model request or child job. Assist and Auto may generate and retain a proposal, but both require explicit native review before saving. Auto does not manufacture a review, change an existing rule, run an experiment, deploy a detector or grant execution authority.

The existing controller owns `detection.ai.create`. Its fixed provider purpose, `bluefire_detection_source_creation`, is enrolled with the exact schema digest in both supported dialects. Only the explicitly selected provider is used, with its existing token, transport and redaction budgets. Input contains selected context, the operator's bounded message, observed field shapes and only metadata permitted by the configured data policy. Evidence references must identify supplied observed records. A deterministic test provider verifies integration; it is not model-quality evidence.

The native URL uses `create_job`. `GET /ai/detection-create-jobs/{id}` returns the immutable proposal, authoritative `review_ready`, exact decision, application job, application receipt and actual evaluation report. Reading never submits work. A published proposal interrupted before callback completion can still be reviewed after reopening, without another provider request.

`POST .../validate` accepts the proposal digest and exact edited title/source. The existing parser/converter checks that source without saving it and returns the server's `reviewed_digest`. Invalid source receives a bounded 422 refusal. `POST .../review` accepts or rejects the exact proposal, with `reviewed_by`; acceptance additionally binds the edited title/source and reviewed digest. Source edits require new validation. The product store's ordinary sensitive-content boundary applies before proposal and review persistence.

Acceptance retains the exact decision and queues `detection.ai.create.apply` on the existing controller. The callback reparses the accepted source, builds the existing bounded run evaluation, then commits the initial candidate, revision index, development evaluation, immutable creation snapshot and both job receipts in one writer transaction. No intermediate registry seed is written. Source, catalog, parser and explicit provider configuration are checked again before publication and commit. Stop wins before commit and rolls everything back; a committed receipt remains available if Stop arrives afterward.

Initial identity derives from the parsed executable query, language and the fixed BlueFire normalized-observation dataset. This is executable-text identity, not a claim that differently formatted SQL is semantically equivalent. Sigma-declared metadata remains in the exact source and parser record; the dataset is not relabeled as target-native telemetry. Existing candidate identities are never overwritten: a collision requires the saved rule's native revision workflow.

Exact decision retries recover a missing or interrupted application using deterministic controller identities. A process loss after commit resolves the existing receipt instead of generating a model request, candidate or evaluation again. The creation snapshot preserves the original report binding when the saved candidate later follows its ordinary lifecycle; its current identity, definition and source must still match. Corrupt or mismatched snapshots and receipts are refused.

The parent result is `detection_created`, with the actual candidate/evaluation references, observed/evidence counts, nullable match count and backend execution state. Every generated evaluation is labeled `development_case: true`. A match on the source used to write the rule is a development measurement; it establishes neither held-out performance nor deployed prevention. The native saved rule can subsequently participate in the existing revision, evaluation and method comparison workflows.
