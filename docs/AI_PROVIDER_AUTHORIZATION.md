# Model data and usage authorization

AI provider configuration and authorization are separate. Settings saves the public API style, exact POST endpoint, model, and optional environment-variable credential reference. Saving or activating that configuration does not permit model traffic. The operator then reviews one finite data and usage decision in the same setup panel. Deterministic operation needs no model authorization.

The supported secret reference is `api_key: {env: ENVIRONMENT_VARIABLE_NAME}`. BlueFire resolves only that explicitly named variable in the server process, or in the operator-owned prepared-lab broker. The interface neither accepts nor displays the secret value. The runner's protected secret store is a different mechanism. Remote providers use HTTPS; an explicitly reviewed loopback provider may use HTTP and may omit a credential reference. A local endpoint is still a model request and requires data and usage authorization.

A `bluefire.ai-live-authorization.v1` decision binds the entire canonical public provider configuration, its digest, the current access context, selected existing assistance purposes, an operator name, an expiry of at most 15 minutes, and explicit usage consent. It permits bounded, redacted lab context: the selected graph and objective, registered method/input/parameter information, relevant observations and evidence references, detection source and evaluation summaries, and operator questions within the chosen purposes. Raw logs, raw traces, evidence bodies and credentials are excluded. Redaction must remain enabled with evidence content omitted and the required secret keys protected. The operator must choose only permitted lab data; content screening does not prove that arbitrary text is non-sensitive.

The three cumulative limits are attempted wire requests, full request bytes, and reserved output tokens. Each actual wire attempt reserves its complete request size and configured output ceiling before dispatch, including retries and network fallback providers when separately authorized. Failures, invalid responses, timeout and cancellation do not refund a reservation because provider work may already have occurred. Output reservation includes any reasoning within the provider's output limit. These are conservative usage limits, not currency budgets or guarantees about provider billing. No request is sent merely by loading, saving, activating or authorizing configuration.

Normal service calls share the same authorization boundary. Before every dispatch it verifies the exact provider, current decision, selected fixed purpose and strict output schema, bounded request shape, redaction policy, expiry and remaining cumulative limits. A changed endpoint, model, credential reference, redaction setting or other provider configuration requires another decision. Revocation, expiry and service shutdown cancel pending requests; late results are discarded. Restart preserves prior decisions and counters, but does not restore their authority. A new decision creates a separate historical record and cannot erase the previous usage.

Prepared-lab authorization narrows the broker's existing exact provider, registered schemas and session expiry through its authenticated channel. Settings cannot enroll a new endpoint, provider or credential. Both the product and broker count attempts; replaying a broker grant cannot reset its counters or resurrect a revoked grant. A failed control acknowledgement closes access and revokes the local decision. Starting a new prepared-lab enrollment remains a separate operator action.

`GET /api/v1/ai/authorizations` returns public context, decisions, status and counters. `POST /api/v1/ai/authorizations` accepts the reviewed exact provider, purposes, `data_scope: reviewed_lab_context`, limits, duration, operator name and explicit usage/local-endpoint decisions. Revocation uses `POST /api/v1/ai/authorizations/{authorization_id}/revoke` with an empty object. These routes use the existing authenticated local browser API boundary. The durable store retains immutable decision documents and append-only attempt reservations separately from model responses.

A connection check sends one synthetic request and is not orchestration evidence. Deterministic provider fixtures test the enforcement software; they are not live-model evidence. Actual live validation must separately retain the provider/model identity, proposals, review decisions, applied actions, observations, outcomes and used-fallback status. Model data authorization never grants runner execution authority or widens an approved experiment.
